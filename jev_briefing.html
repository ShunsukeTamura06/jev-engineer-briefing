Decision Model とは

文章は書かない。選んで、確率を返すだけ

渡すもの（例：Jev の API）

{ "model": "jev-latest", "state": "物価上昇率は見通しに沿って…",① 判断の材料 "questions": { "stance": { "type": "choice", "instructions": "金融政策のスタンスは？",② 問い "criteria": {③ 選択肢 "hawkish": "引き締めに前向き", "neutral": "どちらとも言えない", "dovish": "緩和に前向き" } }} }
→

返ってくるもの

{ "answers": { "stance": { "choice": "hawkish",④ 選んだ答え "probabilities": {⑤ 確率 "hawkish": 0.82, "neutral": 0.15, "dovish": 0.03 } }} }

Q. JSON という「文章」が
返ってきているのでは？

モデルが決めるのは④どれを選ぶかと⑤確率の数字だけ。
JSON の枠は、渡した問いと選択肢を API が決まった形に詰め直したもの。
LLM のように1文字ずつ書いた文章ではない。

LLM が記述式の試験なら、Decision Model はマークシートの試験

確率の意味

同じ「82%」でも、意味が違う

LLM の確率

選ばれる確率

次にその言葉が選ばれる確率。
文章としてのもっともらしさで、当たる確率とは限らない（自信過剰になりやすい）。

Decision Model の確率

合っている確率

「82%」と言ったら、
実際に8割当たることを目指して学習している。

実例：Jev で迷惑メール 18,514通を判定
「0.9 以上」と言ったものの 99.9%、「0.1 未満」と言ったものの 0.1% が本当に迷惑メール

だから確率で分けられる 高い任せる（抜き取り確認） 中くらいLLM で再確認 低い人が判断

学習の狙いは TypeSafe の説明（RLCD）。実例は外部開発者による検証（O'Reilly Radar で紹介、英語のメール）。

「で、どれくらい速いの？」

10秒→0.4秒

25倍速い（費用も 75分の1）

Decision Model の課題

速い代わりに、判断力は最先端に届かない

判断力最先端モデルの答えとの一致率

Opus 5最先端の LLM73%38秒

作り話はしないが、間違った選択肢は選ぶ。→ 5枚目の確率の振り分けで補う

公式が挙げる苦手

  • 計算・数を数える→ 計算はコードで
  • 日付の比較→ 取り出すだけ、比べるのはコード
  • 書いたとおりにしか読まない→ 条件を正確に書く
  • 最初の選択肢に寄りやすい→ 順番を入れ替えて確かめる

まとめ

判断を全件に置き、迷ったものだけ LLM と人へ

選ぶ仕事 → Decision Model

選択肢が決まっている・件数が多い・速さが要る。
振り分け・絞り込み・確認

書く仕事 → LLM のまま

文章・要約・コードを書く。
理由の説明が要る判断

判断力　―　最先端の LLM には届かない

同じ水準の判断が、時間 25分の1・費用 75分の110秒 → 0.4秒

精度の不足は確率で補い、強い LLM と人の時間は迷うものだけに

補足｜社内で使うには

社内のデータは、社内で動く Kev で

1

動かす

社内のクラウド検証環境（GPU 1枚）で稼働中。データを外に出さない。

2

つなぐ

Jev と同じ形の API。
接続先を変えるだけで、後から Jev にも切り替えられる。

3

測る

正答率は Jev と 2pt 以内、確率の当たり方は Jev が上。しきい値は自分のデータで測って決める。
